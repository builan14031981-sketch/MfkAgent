🚀 MfkAgent AI 接手生存指南 (v85.0)
核心定位：MfkAgent 已从“聊天壳子”进化为本地化 AI Agent 助手平台。
核心链路：用户 ➔ Chat ➔ AgentRuntime ➔ Planner/TaskGraph ➔ Tool执行 ➔ 验证 ➔ 沉淀Memory。

一、 核心架构现状 (你在操作什么)
1. 后端 AI 引擎 (AgentRuntime)
统一入口与规划：所有 Agent 走统一 Runtime，由 Planner 进行任务拆解 (TaskGraph DAG)，支持动态自愈（失败 ➔ Reflection分析 ➔ 插入修复节点）。

Persona V2 (人格运行时)：严禁把几千字塞进 System Prompt。

知识已拆分为 .md 文件 (配置在 profiles/、expression/、behavior/ 等)。

支持“表达预算”(Expression Budget)，从机制上限制 AI 过度表演、滥用 emoji。

支持关系层 (pianai 专属)，根据用户互动次数动态切换关系阶段和情绪。

工具与工作区感知：

工具分级：未绑定项目的普通聊天不再“全禁工具”，add_memory/web_search 等无路径工具默认可用。

路径感知：若用户聊天中发送绝对路径，系统会自动将其设为临时工作目录，解锁文件级工具。

多模态与权限：支持文本/图片/二进制附件上传（自动走 Vision 路由）；已实现 auto_approve 自治模式（按需绕过人工确认，高危操作除外）。

2. 前端与客户端 (UI & Electron)
字体与主题：已实现零外网依赖的本地化构建；主题切换实现了缓存直读（解决了闪黑 FOUC 问题）。

UI 状态持久化：侧边栏折叠、任务卡片折叠、上下文面板开关等已接入本地持久化（刷新不再重置）。

信息流收敛展示 (极简风)：

废弃了花哨的边框和动画。思考过程、记忆保存提示等全部收敛为无框单行文本。

ToolCallGroup：连续的工具调用被折叠为一组（摘要组头），只在失败或耗时较长时凸显，极大降低了视觉噪音。

桌面端集成：Electron 链路已打通（后台 ➔ 前端 ➔ 客户端），修复了 Windows Toast 消息通知防堆叠和 AUMID 识别问题。

二、 历史包袱与避坑指南 (重要数据流)
Timeline (时序事件) 机制：

前后端解耦：后端的 Message.timeline 已修复，能正确记录 文本 ➔ 工具 ➔ 文本 的真实交错时序。

前端渲染：前端 ChatMessage 会严格消费 Timeline 数据来还原真实的对话和工具执行顺序，不要轻易改动前端的渲染顺序回退逻辑。

API Key 策略：不再做后端强制脱敏，用户在本地拥有绝对控制权（保留明文）。

单例陷阱：后端的权限模式 (agent_permission_mode) 已修复热重载机制。若后续修改全局配置，切记同步更新内存单例，避免读库延迟。

工具组防误删：MessageList.tsx 的 `case "tool": return null` 分支运行时不会命中（工具段已被 ToolCallGroup 分组提前消费），但它是 TS 类型收窄必需的，删除会导致 default 分支把无 title/content 的工具事件纳入而类型报错。勿删。ToolCallCard / ToolCallCardList 已标 @deprecated 保留（不删原则），新代码一律用 ToolCallGroup。

三、 下一阶段任务 (What to do Next)
当前阶段的核心不再是“堆新功能”，而是“增强作为工作助手的体验”。

🎯 高优方向：

Memory 2.0 (认知记忆)：从“简单存储”升级为“认知系统”，让 Agent 能建立长期用户理解。

Agent 状态可视化与 Timeline 增强：类似 Claude Code，向用户清晰展示“规划 ➔ 拆解 ➔ 执行 ➔ 验证”的流转过程。

核心能力爬升：持续优化 Planner 的任务拆解质量、工具调用准确率以及失败后的自我修复 (Reflection) 能力。

四、 绝对禁区 (DO NOT DO) 🚫
以下方向已被项目组明确归档废弃，接手的 AI 在任何情况下不要往这些方向写代码：

❌ MCP 生态 (不搞复杂协议生态)

❌ Plugin 市场 (不需要插件化商店)

❌ Workflow 编辑器 (不搞图形化连线排版)

❌ AutoTask 平台化 (不做云端任务托管平台)

修改代码的安全纪律：

历次重要修改（尤其是 UI 和引擎）在 _backup/ 目录下均有备份，动手改动核心渲染（如 ChatMessage.tsx 或 context_builder.py）前，必须确保可随时回滚。

前端代码目前的 ESLint 基线存在几十个无关的旧 warning，不要强迫症发作去清理与你当前任务无关的 lint 警告，聚焦手头需求。

五、 已审查的借鉴清单与暂缓方向（2026-08-14 · deepseek-harness 深度审查）🚧
把已做过的架构审查结论固化在这里，避免后续重复评估或误开工。完整决策记录在《归档/旧版文档/交接文档8.10.md》2026-08-14 条目。

P0（已落地，勿重做）：
工具展示纯函数可回放：normalizeToolCall / resolveToolMeta / groupToolCalls 全为纯函数，流式 timeline 与历史回放共用同一套分组与标题推导，保证直播与历史渲染一致。
截断带总量标记：大日志截断处标注"已截断（共 N 字符）"，防止把半截结果当全貌（对应 dsh 的 truncated/total 语义）。
流式防冒充：工具组流式中只显示一行头（spinner + N/M + 当前工具名），结束才收敛为摘要，过程状态不落库。

暂缓（触发条件未到，勿提前做）：
arguments_raw：工具参数 raw JSON 保真（后端 tool_start 增字段）——涉及后端协议，当前 args 仅展示用，性价比低；将来需要时是 additive 零破坏。
会话日志统一事实源：把 DB 消息 + UI timeline 双轨收敛为"事件流 + 推导投影"——等高价值需求（subagent / fork / 多会话共享）真正立项再评估，别为做而做。
接缝三件套（fs/shell/search 留 provider 接口层）：每个能力目前只有单一实现，划接口徒增抽象；与上方"绝对禁区"（不搞 MCP / 不搞插件化）同一道理。约定：工具域集中在 tool_registry + execute_tool 单一模块，消费者不 import 实现内部。
事件三分域：已核实天然满足——tool_start/tool_result 持久为 RuntimeEvent 事实，流式运行态（isSending、running 工具、N/M）只在 store 里不落库，无需动作。

理念（随用随取，不必主动做）：
输入通道分层（普通追问 / 打断改向 / 注入上下文显式化）、安全单调性（审批/守卫只能收窄、不能靠顺序翻案——ApprovalPolicy 已是单一决策链）、文档记录三段式（问题/决策/取舍）。
