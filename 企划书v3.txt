# MfkAgent 产品企划书 V4.0

**版本：V4.0**
**状态：产品方向确认版（核心闭环已实现）**
**用途：MfkAgent 长期产品设计基准文档**

---

# 一、产品定位

## 产品名称
MfkAgent

## 1.1 产品定义
MfkAgent 是一款：
> 面向个人开发者、专业用户的 AI 工作助手。

它通过：
- AI 对话
- 项目上下文管理
- 文件理解
- 模型调用
- 个人记忆

帮助用户完成真实工作任务。

## 1.2 核心理念
MfkAgent 不追求：
> 拥有最多 AI 功能。

而追求：
> 成为一个长期可靠的个人 AI 工作伙伴。

核心体验：
```
用户目标 → 工作环境 → AI理解上下文 → 提供分析/建议/辅助 → 沉淀工作过程
```

---

# 二、产品方向

## MfkAgent 是什么
MfkAgent 是：
```
AI 工作空间
```
而不是：
```
聊天机器人
```

区别：

| 普通聊天 | MfkAgent |
|----------|----------|
| 用户 → 问题 → 回答 | 用户 → 项目 → 任务 → 上下文 → AI协作 → 结果沉淀 |

---

# 三、产品边界

## 3.1 不做的方向

### ❌ ChatGPT 网页复刻
MfkAgent 不只是聊天窗口。

### ❌ AI 玩具集合
禁止：大量无意义 AI 功能堆叠、娱乐化功能优先、功能展示大于实际价值。

### ❌ Agent 制作平台（V1 阶段禁止）
- 用户创建 Agent
- Agent 编辑器
- Agent 市场/分享/发布

> MfkAgent 的目标不是让用户制造机器人，而是提供经过设计的 AI 工作伙伴。

### ❌ 复杂自动化平台
暂不做：Workflow Builder、节点编辑器、自动任务编排。

### ❌ 插件生态
暂不做：Plugin Marketplace、MCP 管理中心。

---

# 四、核心产品结构

```
Workspace → Project → Chat → Message → Agent → Model
```

---

# 五、Workspace 设计

## 定义
Workspace 是用户的 AI 工作空间，负责管理项目、聊天、上下文。

## 5.1 Project
Project 是核心工作单位。

示例：MfkAgent项目、Minecraft项目、简历优化、个人网站

Project 包含：
```
Project { id, name, path, createdAt, updatedAt }
```

**注意：Project ID 与路径必须分离，避免文件路径变化导致数据失效。**

---

# 六、Chat 设计

## Chat 定位
Chat 是用户与 AI 的一次持续工作过程。

关系：
```
Project → Chat → Message
```

支持：
- **普通聊天**：无项目关联（User → Chat → Message）
- **项目聊天**：属于某个 Project（Project → Chat → Message）

---

# 七、Agent 设计原则

## 7.1 Agent 定义
MfkAgent 中的 Agent：
> 一个具有固定工作方式、行为规则和能力范围的 AI 工作角色。

结构：
```
Agent → Identity → Behavior → Personality → Capability → Model
```

## 7.2 Agent 产品原则
**V1：只提供系统预设 Agent。**

用户可以：✅ 选择、✅ 使用、✅ 调整部分行为参数  
用户不能：❌ 创建、❌ 修改核心 Prompt、❌ 发布、❌ 分享

## 7.3 预设 Agent 方向
| Agent | 定位 | 特点 |
|-------|------|------|
| 小暖 | 温暖陪伴型 | 理解用户状态、提供支持、降低压力 |
| 理性分析师 | 决策审查型 | 检查逻辑、发现风险、挑战假设 |
| 代码助手 | 软件开发辅助 | 分析代码、架构建议、关注维护成本 |
| 产品经理 | 产品决策支持 | 需求分析、优先级排序、风险评估 |
| 代码审查 AI | 代码质量把关 | 代码规范、架构合理性、长期维护 |
| 前端 UI 设计 AI | 界面设计协助 | 设计规范、组件建议、交互优化 |
| 后端 AI | 后端开发协助 | API设计、数据库、性能优化 |
| 笔神 | 写作助手 | 文案润色、结构梳理、风格适配 |

---

# 八、人格系统设计

## 8.1 设计目标
用户可以调整：> AI 回应方式。
不是修改：> AI 身份。

## 8.2 理性感性系统
五档：
```
极度感性 (0%) → 偏感性 (25%) → 平衡 (50%) → 偏理性 (75%) → 极度理性 (100%)
```

## 8.3 Prompt 组合原则
禁止：简单修改 temperature。  
采用：动态 Prompt 组合。

结构：
```
系统规则 + Agent身份 + 人格参数 + 用户偏好 + 任务上下文 → 最终 System Prompt
```

---

# 九、Memory 设计原则

## 9.1 Memory 定位
用于保存长期有效信息。

示例：
- 用户偏好：喜欢简洁回答
- 项目记忆：MfkAgent 使用 Electron

## 9.2 Memory 不做
禁止：复杂知识库替代品、自动收集所有聊天、无限制保存信息。

---

# 十、项目文件感知原则

## 10.1 目标
让 AI 理解用户正在工作的内容。

流程：
```
Project → 文件结构 → 上下文分析 → AI辅助
```

## 10.2 V1 限制
支持：文件读取、文件上传、项目说明  
不做：自动修改代码、自动重构项目

---

# 十一、UI 设计规范

## 11.1 设计目标
> 简洁如聊天软件，专业如开发工具。

## 11.2 页面视觉层级
| 层级 | 用途 | 规范 |
|------|------|------|
| 品牌展示层 | 首页入口 | 标题 36-48px，欢迎语 16-20px |
| 页面标题层 | 设置/管理页 | 20-24px |
| 模块标题层 | 功能区域标题 | 16-18px |
| 内容层 | 正常信息展示 | 14-15px |
| 辅助层 | 说明/状态/提醒 | 12-13px |

## 11.3 首页规范
结构：品牌展示 → 欢迎引导 → 输入区域 → 辅助提示  
允许：大留白、简洁视觉中心、明确入口  
禁止：大量功能入口、信息堆叠、多视觉中心

## 11.4 工作空间规范
进入 Project 后：Sidebar + 主工作区域，连续体验。  
禁止：传统网页跳转感。

## 11.5 动画规范
允许：opacity、transform、轻微位移、淡入淡出  
禁止：大范围移动、长时间动画、炫技动画

---

# 十二、前端组件规范

## 12.1 组件职责
每个组件必须有明确职责。  
禁止：一个页面包含大量业务逻辑。  
推荐：Page → Container → Component → Element

## 12.2 定位规范
禁止：全局 absolute/fixed 控制页面布局。  
正确：页面容器 → 功能区域 → 组件容器 → 内部元素

## 12.3 样式规范
禁止：大量硬编码颜色。  
必须：使用 CSS Variables 统一管理主题/背景/文字/边框。

---

# 十三、数据架构规范

最终关系：
```
User → Workspace → Project → Chat → Message
```
Agent 关系：
```
Agent → Chat 使用 Agent
```
禁止：`Agent 拥有 Chat`

---

# 十四、国际化规范
所有用户可见文字必须进入语言资源。

结构：
```
locales/
├── zh-CN
└── en-US
```

禁止：直接写死中文/英文。

---

# 十五、模型系统原则
模型属于执行层。

关系：
```
Agent → Model Service → API → 模型
```

支持：模型选择、API 配置、默认模型。

---

# 十六、开发协作规范

## 16.1 文档体系
MfkAgent 使用三个核心文档：
```
产品企划书 → 开发计划书 → 项目交接文档
```

| 文档 | 负责 | 修改时机 |
|------|------|----------|
| 产品企划书 | 长期方向 | 产品方向变化时 |
| 开发计划书 | 开发路线 | 阶段调整时 |
| 项目交接文档 | 当前代码状态 | 每次开发阶段更新 |

---

# 十七、AI 并行协作与交接规范

## 1. AI 角色划分

MfkAgent 开发过程中，根据职责分为三个核心 AI 角色：

### 后端 AI（Backend Agent）
**负责：**
- 后端架构
- 数据库设计
- API 设计与实现
- AI Runtime（模型服务、工具调用、Prompt 组合）
- 服务逻辑与数据处理

**不负责：**
- UI 设计
- 页面交互
- 用户体验设计

### 前端 AI（Interface Agent）
**负责：**
- 页面开发与路由
- UI 组件库
- 用户交互与状态管理
- 主题系统
- 前端 API 接入与数据流

**不负责：**
- 后端架构调整
- 数据库设计
- API 核心逻辑修改

### 计划 AI（Planning Agent）
**负责：**
- 产品方向决策
- 阶段规划与里程碑
- 任务拆分与优先级排序
- 计划书维护与版本管理

---

## 2. AI 开发前读取规范

任何 AI 开始开发前，必须按顺序读取并确认：

```
产品企划书
    ↓
开发计划书
    ↓
最新交接文档
```

确认内容：
- 当前产品目标
- 当前开发阶段
- 当前代码状态
- 自己负责的范围边界

---

## 3. 后端 AI 交接规范

后端 AI 完成任务后，必须更新交接文档，包含：

| 项 | 说明 |
|----|------|
| **完成内容** | 例：创建 Project 模型、增加 /api/projects 接口、完成 CRUD 测试 |
| **修改文件** | 例：`backend/models/project.py`、`backend/api/projects.py` |
| **对前端影响** | 说明前端 AI 是否需要同步修改 |
| **API 说明** | 新增/修改接口必须标注：请求方式、地址、参数、返回结构 |

---

## 4. 前端 AI 交接规范

前端 AI 完成任务后，必须更新交接文档，包含：

| 项 | 说明 |
|----|------|
| **完成内容** | 例：Sidebar 项目列表显示、接入 Project API、增加项目切换交互 |
| **修改文件** | 例：`src/components/Sidebar.tsx`、`src/hooks/useProjects.ts` |
| **后端依赖** | 当前功能依赖哪些后端接口 |
| **UI 变化** | 用户可见的变化对比（原→现） |

---

## 5. AI 间协作原则

| 原则 | 说明 |
|------|------|
| **不跨域修改** | 前端 AI 禁止修改数据库结构；后端 AI 禁止修改页面布局 |
| **跨域流程** | 发现需跨域修改 → 在交接文档说明 → 等待负责 AI 处理 |
| **并行开发** | 允许前后端并行，但必须：修改范围明确 → 避免同文件冲突 → 通过交接文档同步状态 |

---

## 6. 交接文档定位

交接文档**不是开发日志**，只记录当前系统状态：
- 已完成能力
- 当前接口清单
- 页面状态
- 已知问题
- 下一步任务

目标：让任何 AI 接手项目时，能快速理解当前状态。
