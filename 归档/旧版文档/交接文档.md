### 2.4.1 TaskRouter（Phase 2）

**职责**：根据用户消息 + tool_runtime decision 判断任务类型，不重新调用 IntentAnalyzer。

**TaskType 枚举**（6 类）：
| 类型 | 触发条件 | 示例 |
|------|----------|------|
| CHAT | 闲聊/问候关键词 | "你好"、"谢谢" |
| CODE | 代码关键词（python/bug/函数/类等） | "这段代码有什么问题" |
| ACTION | 操作关键词（创建/修改/删除/执行等） | "帮我创建文件" |
| RETRIEVE | 查找/搜索/读取关键词 | "查找文件"、"是什么" |
| ANALYZE | 分析/检查/评估关键词 | "分析这段代码"、"为什么报错" |
| ANSWER | 默认（未命中任何规则） | 一般问答 |

**决策结果**（`TaskDecision`）：`task_type` / `intent` / `confidence` / `reason`

**在 agent.py 中的使用**：
```python
decision = self.router.route(
    message=user_message,
    tool_decision=context.decision,  # tool_runtime 的 decision
    has_tools=has_tools,
)
# 决策结果写入 AgentResult.metadata
```

### 2.4.2 Execution Loop v1（Phase 3）

**职责**：控制多轮工具调用流程，从"任务判断器"升级为"执行控制器"。

**核心常量**：`MAX_ROUNDS = 3`

**执行流程**：
```
User Message → AgentRuntime.run()
  → TaskRouter.route() → 判断任务类型
  → Execution Loop（最多 MAX_ROUNDS 轮）:
      每一轮: call_once() → 单次 LLM 调用
        ├── 无 tool_calls → 最终回答，退出循环
        └── 有 tool_calls → 执行工具 → 回喂结果 → 继续循环
  → 返回 AgentResult（content / rounds / finish_reason / tool_calls / metadata）
```

**关键设计决策**：
- 最后一轮（`round_no >= MAX_ROUNDS - 1`）强制 `tools=None`，确保模型返回文本
- 轮次耗尽无内容时，补一次无工具调用获取总结
- 非流式路径不支持审批 → 自动拒绝并回喂错误

**新增依赖**：`model_service.call_once()`（`backend/app/services/model.py`）
- 新增 `SingleCallResult` 数据类（content / tool_calls / finish_reason / usage）
- 只做单次 API 请求，不负责工具循环/重试/决策
- 与 `chat()` 区分：`chat()` 内部有 8 轮 Tool Calling 循环，`call_once()` 只做一次

**AgentResult 字段**：
| 字段 | 类型 | 说明 |
|------|------|------|
| content | str | 最终回复文本 |
| usage | dict | token 用量 |
| rounds | int | 执行轮次（含最终回答轮） |
| finish_reason | str | "stop" / "max_rounds" |
| tool_calls | list | 工具调用记录列表 |
| metadata | dict | agent_id / model_id / task_type / intent / confidence |

**chat.py 集成**（`send_message` 端点，非流式）：
```python
agent_runtime = AgentRuntime()
agent_result = await agent_runtime.run(
    context=agent_context,
    messages=model_messages,
    temperature=..., max_tokens=..., reasoning_effort=...,
    read_only=(chat_mode == "plan"),
)
ai_content = agent_result.content
```

**测试**：`backend/tests/test_agent_runtime_phase3.py`（7 个用例，**全部通过**）
- 普通聊天、单工具调用、多轮工具调用、工具失败、MAX_ROUNDS 限制
- 无工具可用、memory_text 仅首轮注入
- 通过 mock 实现，无需真实 API 调用
- **测试结果：7 PASS / 0 FAIL，无需代码修改**

### 2.4.4 Timeline 持久化（V1 — v70.0）

**问题**：`send_message_stream` 流式过程中 SSE 事件顺序正确（thinking→tool_start→tool_result→text），但 stream 完成后 `appendAssistant` 将其降级为传统 `Message { content, thinking, tool_calls }`，导致 Agent 执行轨迹顺序丢失。

**方案**：在 `Message` 模型新增 `timeline` JSON 字段，流式过程中同步累积 `timeline_events`，持久化时一并写入。

**timeline JSON 结构**：
```json
[
  {"type": "thinking", "content": "..."},
  {"type": "tool_start", "tool_call_id": "call_001", "tool": "read_file", "input": {...}},
  {"type": "tool_result", "tool_call_id": "call_001", "tool": "read_file", "success": true, "result": "...", "duration_ms": 120},
  {"type": "text", "content": "分析完成..."}
]
```

**改动文件**：
- `app/models/agent.py` — Message 模型新增 `timeline = Column(JSON)`
- `app/api/chat.py` — `generate()` 累积 `timeline_events`；持久化写入 `timeline`；`send_message` 从 AgentResult 构造 timeline；`MessageResponse` 新增 `timeline` 字段
- `main.py` — `_ensure_schema()` 自动迁移 `timeline` 列

**兼容性**：
- 旧字段 `content`/`thinking`/`tool_calls` 保持不变，双写
- 旧消息 `timeline` 为 NULL，前端可降级到旧渲染逻辑
- SSE 协议不变，AgentRuntime 不变

**测试**：`tests/test_timeline_persistence.py`（3 用例，全部通过）
- Tool Agent：验证 thinking→tool_start→tool_result→thinking→text 顺序
- Normal Chat：验证 timeline 仅含 `[{"type": "text", ...}]`
- Tool Error：验证 tool_result 中 `success: false` 被正确保存

## 2.7 Planner G2-B — LLM 辅助规划（Phase G2-B）

**目标**：将 G1 规则模板 Planner 升级为 LLM 辅助 Planner，保留 heuristic fallback。

### 2.7.1 架构

```
PlannerService
    |
    +-- HeuristicPlanner（_plan_heuristic）
    |
    +-- LLMPlanner（model_service.call_once()）
```

**G2-B 流程**：
```
User Request → ContextBuilder → PlannerService.plan()
    ├── planning_level < 2  → _plan_heuristic()（纯规则模板）
    └── planning_level >= 2 → LLMPlanner.plan()
            ├── 成功 → 解析 Plan → 返回
            └── 失败 → fallback → _plan_heuristic()
```

### 2.7.2 PlanningLevel 层级控制

**新增** `PlanningLevel` 类（`models.py`）：

| 常量 | 值 | 含义 |
|------|-----|------|
| `HEURISTIC` | 0 | 纯启发式规则模板 |
| `BASIC` | 1 | 基础规则模板 |
| `LLM` | 2 | LLM 辅助规划 |
| `LLM_THRESHOLD` | 2 | 允许 LLM 的最低 Level |

```python
PlanningLevel.allow_llm(level)  # level >= 2 → True
```

### 2.7.3 LLMPlanner

**新增** `llm_planner.py`：
- 无状态单例（`get_llm_planner()`）
- 使用 `model_service.call_once()` 单次 LLM 调用（temperature=0.3, tools=None）
- 不负责工具循环、不控制执行、不修改 AgentRuntime
- `_parse_response()` 处理 JSON 解析（支持 ````json` 包裹）、字段缺失、空 steps
- 失败时抛出异常，由 PlannerService 捕获后 fallback heuristic

**System Prompt**：要求 LLM 输出结构化 JSON（goal/steps/constraints），步骤数 1-5 个。

### 2.7.4 PlannerService 升级

`PlannerService.plan()` 新增参数：
- `planning_level: Optional[int]` — 层级控制（None/0/1=heuristic only）

## 2.9.2 Scheduler / Executor 架构前置调查（Phase G4-D，只读调研）

> **状态**：调研完成，未改任何代码、未创建任何模块。为 G4-D Scheduler/Executor 抽象提供设计依据。

### 2.9.2.1 当前代码结构分析

**AgentRuntime（`agent.py`）**：
- TaskGraph 外层循环（2 处，近亲复制）：`run()` 非流式 `agent.py:562-664`；`_run_stream_events()` 流式 `agent.py:813-973`
- 单 Task 执行逻辑（2 处，重复）：`run()` 内层 `agent.py:589-648`（MAX_ROUNDS=3，call_once）；流式内层 `agent.py:846-953`（MAX_STREAM_ROUNDS=8，stream_once + Normalizer 兜底）
- Tool execution loop（共用）：`_exec_tool_calls` `agent.py:322-387` → `_exec_tool_calls_with_verification` `agent.py:389-433`（实际执行在 `tool_runtime/executor.py:execute_tool`）
- Verification loop：`agent.py:420` `verifier.verify_all()`；失败注入【验证反馈】驱动下一轮（`agent.py:426-433`）
- Event emission（双通道）：非流式 recorder.emit/transition/finish_run（`recorder.py`）；流式 run_stream() 包装器统一持久化 + yield（`agent.py:746-761`）

**任务生命周期处理位置**：
| TaskNode 状态 | 非流式 | 流式 | 责任者 |
|---|---|---|---|
| pending | TaskGraphState.from_plan 默认态 | 同左 | TaskGraphState |
| running | `agent.py:571` | `agent.py:829` | AgentRuntime |
| completed | `agent.py:653` | `agent.py:909/928` | AgentRuntime |
| failed | `agent.py:662` → `_handle_task_failure` → mark_failed | `agent.py:958`（内联） | AgentRuntime |
| skipped | mark_failed 级联 / mark_pending_skipped | 同左 | AgentRuntime |

**关键观察**：
- 状态机本身（`task_graph_state.py`）已足够干净（无 DB、无事件依赖），真正要抽的是 AgentRuntime 里的编排循环与单 task 内层执行。
- run() 与流式差异仅 3 处：事件出口（emit vs yield）、审批支持（False vs True）、流式多 Normalizer + 兜底总结（MAX_ROUNDS vs MAX_STREAM_ROUNDS）。
- `memory_text` 注入条件 `round_no == 0 and not has_task_graph`（`agent.py:599,860`）与 TaskGraph 耦合，抽 Executor 时必须保留。
- 审批是跨 task 全局副作用（`approval_registry`，chat.py 层 `cancel_by_chat`），不能收进单 task Executor 内部。

### 2.9.2.2 推荐 G4-D 架构

```
TaskGraph（G3，只读）→ TaskScheduler（决策）→ TaskExecutor（单 task 执行）→ AgentRuntime（编排）
  · TaskScheduler：消费 TaskGraphState（依赖注入，不重写），对外 next_task()/mark_running/completed/failed/skipped()，
    内部含级联与收敛逻辑；无 DB、无事件、无 I/O，纯同步可测。
  · TaskExecutor：async run_task(task, ctx, ...) → 事件流；封装内层 LLM 循环（call_once/stream_once 参数化）、
    工具执行、验证、反馈注入、persona、Normalizer；不碰 AgentRun/recorder，只 yield 业务事件。
  · AgentRuntime：保留编排，收敛双循环；由 Scheduler 给任务、Executor 产事件、Runtime 决定落库 or yield。
```

**关键决策建议**：Scheduler **不要替换** TaskGraphState（它已是正确抽象），只做其"策略消费者"；否则 G4-A/B/C 已验证用例需全量重写，风险剧增。

### 2.9.2.3 建议新增 / 修改文件

**新增**：
- `backend/app/core/agent_runtime/scheduler.py` — TaskScheduler（从 AgentRuntime 抽 task 循环决策）
- `backend/app/core/agent_runtime/executor.py` — TaskExecutor（从 AgentRuntime 抽单 task 内层执行）
- `backend/tests/test_task_graph_scheduler_phase_g4d.py` — Scheduler 单测（就绪决策/状态流转/级联/收敛/进度）
- `backend/tests/test_task_graph_executor_phase_g4d.py` — Executor 单测（mock model_service：轮次/工具/验证/兜底/事件顺序）

### 2.9.2.4 风险评估

| 风险 | 等级 | 说明 |
|---|---|---|
| Runtime 主链影响 | 高 | run()/run_stream 内层循环为最热路径，抽 Executor 须逐参数等价迁移（call_once/stream_once、memory_text 注入） |

**建议实施路径**：两段式 — ① 先抽 Scheduler 纯逻辑加单测（行为不变）；② 再收敛内层执行到 Executor（参数切换流式/非流式）。每段跑全量回归后再继续。

## 2.13 TaskGraph 动态自愈与反思（Phase G4-E，v74.2）

**目标**：当 TaskGraph 中任务节点执行失败时，拦截失败并喂给 LLM 进行反思，允许 LLM 动态注入修复任务。

**核心实现**（`agent.py`）：
- `_reflect_and_heal(current_task, error, model_id, run_id)` — 构造 Reflection Prompt → 调用 LLM 分析错误 → 解析 JSON 修复方案 → 动态注入修复任务
- `_handle_task_failure` 改为异步方法，集成反思逻辑
- 流式异常处理添加反思事件

**Reflection Prompt 模板**：
```
任务 [{task.action}] 刚刚遭遇了严重失败，错误信息为: {error}。
请分析原因，并输出一个新的行动计划（Task）。如果你能修复它，请返回一个新的工具调用或操作指令。
```

**动态注入**（`task_graph_state.py`）：
- `dynamic_append_task(action, parent_task_id, suggested_tools, assigned_agent, task_type)` — 运行时向 TaskGraph 插入新节点
- 自愈策略：父节点 FAILED/RUNNING → COMPLETED，修复节点成为其后继
- 节点 ID 格式：`heal_{counter}`（自增计数器）

**降级保障**：
- LLM 调用失败 → 降级，返回 False
- JSON 解析失败 → 降级
- LLM 判断无法修复（fix_action 为空）→ 降级
- Reflection 失败 → 优雅回退到原彻底失败状态
