MfkAgent Planning & Reasoning Architecture V1.0
一、文档定位

定义：

Agent 如何理解目标、拆解任务、制定计划、调整策略，并完成复杂工作的决策机制。

负责：

Goal理解
Task拆解
Plan生成
Step管理
Decision机制
Replanning

不负责：

Tool具体实现
Memory存储
UI展示
二、核心理念

Agent 的核心能力：

不是：

生成更多文字。

而是：

找到完成目标的最佳路径。

错误：

用户目标

↓

直接生成答案

适用于：

问答
简单咨询

Agent模式：

用户目标

↓

理解目标

↓

设计方案

↓

执行步骤

↓

检查结果

↓

调整方案
三、Goal Architecture（目标系统）

Agent 首先必须识别：

用户真正目标。

用户表达：

通常不是完整目标。

例如：

用户：

帮我做一个网站。

表面目标：

生成网站代码

真实目标：

获得一个可以运行的网站产品

因此：

Agent需要区分：

User Request

用户说了什么。

User Goal

用户想达成什么。

结构：

User Request

↓

Goal Extraction

↓

Goal Definition
四、Goal结构

标准 Goal：

{
 "objective":"",
 "expected_result":"",
 "constraints":"",
 "success_condition":""
}

例如：

{
"objective":"创建个人主页",

"expected_result":
"一个可访问的网站",

"constraints":
"使用React",

"success_condition":
"页面正常运行"
}
五、Task Decomposition（任务拆解）

复杂目标：

不能一步完成。

需要拆：

Goal

↓

Task

↓

Step

示例：

目标：

创建网站。

拆解：

1. 分析需求

2. 设计页面结构

3. 创建项目

4. 编写组件

5. 测试运行

6. 优化
六、拆解原则
原则1：步骤必须可执行

错误：

完成网站

正确：

创建首页组件
原则2：步骤必须可验证

错误：

优化代码

正确：

检查组件重复逻辑并减少重复代码
原则3：避免过度拆解

错误：

把简单任务拆成：

100个步骤。

原则：

保持：

足够详细

但不过度复杂
七、Plan Architecture（计划结构）

Agent生成：

Plan。

结构：

{
"goal":"",

"steps":[

{
"id":1,

"description":"",

"required_capability":"",

"expected_output":"",

"status":"pending"

}

]
}

示例：

Goal:
修复Excel启动问题


Steps:

1.
检查错误日志

Output:
错误原因


2.
定位插件冲突

Output:
问题组件


3.
修复配置

Output:
Excel正常启动
八、Planning Level（规划等级）

不是所有任务都需要完整计划。

分级：

Level 0：直接回答

例如：

"Python是什么？"

流程：

Answer
Level 1：简单任务

例如：

"帮我改一句话。"

流程：

Understand

↓

Execute
Level 2：多步骤任务

例如：

"帮我写一份报告。"

流程：

Plan

↓

Execute
Level 3：复杂项目

例如：

"开发一个软件。"

流程：

Analyze

↓

Plan

↓

Execute Loop

↓

Verify
九、Reasoning Architecture（推理机制）

Agent 不应该：

无限思考。

需要：

结构化判断。

推荐：

Observation

↓

Analysis

↓

Decision

↓

Action

例如：

发现报错：

Observation：

程序启动失败

Analysis：

可能依赖缺失

Decision：

检查依赖

Action：

执行检查
十、Decision Making（决策）

Agent每一步需要判断：

三个问题：

1.

当前目标是什么？

2.

下一步最有效动作是什么？

3.

执行后如何验证？

形成：

Goal

↓

Next Best Action

↓

Verification
十一、Replanning（重新规划）

真实环境：

不会永远成功。

所以：

Agent必须允许修改计划。

流程：

Plan

↓

Execute

↓

Unexpected Result

↓

Analyze

↓

Update Plan

↓

Continue

例如：

计划：

安装依赖

↓

运行项目

发现：

依赖冲突。

重新：

检查版本

↓

调整配置

↓

重新运行
十二、避免错误规划
错误1：没有目标直接行动

例如：

用户：

"帮我优化项目。"

Agent：

直接修改代码。

错误。

应该：

先确认：

优化什么？
目标是什么？
错误2：计划过度

例如：

简单问题生成几十步。

降低体验。

错误3：没有验证

错误：

执行完成

↓

告诉用户完成

正确：

执行

↓

检查

↓

确认
十三、Human Approval机制

规划阶段必须判断风险。

低风险：

自动执行：

阅读
分析
生成建议

高风险：

请求确认：

删除
发布
大范围修改

流程：

Plan

↓

Risk Assessment

↓

Need Approval?

↓

Execute
十四、Planner 与 Executor 分离

重要原则：

不要让一个模块同时：

决定做什么。

又：

执行怎么做。

结构：

Planner

负责：

为什么做

做什么


↓

Executor

负责：

怎么做
