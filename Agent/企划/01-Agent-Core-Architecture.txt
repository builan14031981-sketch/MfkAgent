继续。

这一部分我们不讨论代码实现，而是先把 **Agent Core 的产品与架构边界定下来**。因为 Agent 是 MfkAgent 的核心，如果这里混乱，后面会像之前 Agent/personality 一样不断迁移。

---

# MfkAgent Agent Core V2.0 架构规范（Draft）

## 一、核心定义

MfkAgent 中的 Agent：

不是：

> 一个带名字的 Prompt。

不是：

> 一个聊天角色。

而是：

> 一个具备目标理解、任务规划、能力调用、执行反馈和结果验证能力的 AI 工作主体。

---

# 二、Agent 完整模型

最终结构：

```
Agent

│
├── Identity
│
├── Personality
│
├── Behavior
│
├── Knowledge
│
├── Capability
│
├── Planning
│
├── Execution
│
└── Verification
```

---

# 三、Identity（身份层）

## 定义

回答：

> "你是谁？"

负责：

* 职业定位
* 专业领域
* 核心目标

例如：

## Code Agent

```
Identity:

你是一名高级软件工程师。

你的目标：
帮助用户开发、维护和优化软件项目。
```

---

## 注意

Identity 不应该包含：

❌ 说话风格

❌ 具体任务流程

❌ 工具调用规则

否则会造成耦合。

---

# 四、Personality（表达层）

## 定义

回答：

> "你怎么和用户交流？"

负责：

* 语气
* 情绪
* 表达方式

例如：

同一个 Code Agent：

```
Personality A:

耐心教学型


Personality B:

严格审查型
```

---

规则：

Personality 不改变：

* 专业能力
* 决策逻辑
* 工具权限

只影响：

最终表达。

---

# 五、Behavior（工作行为层）

这是新增核心。

## 定义

回答：

> "你如何完成工作？"

Behavior 决定：

Agent 的工作习惯。

---

例如：

## Conservative Engineer

```
行为：

优先稳定方案

修改前分析影响

避免破坏已有代码
```

---

## Fast Prototype Engineer

```
行为：

快速验证

优先产出结果

允许实验性方案
```

---

Behavior 是 Agent 区别于普通聊天机器人的关键。

---

# 六、Capability（能力层）

## 定义

回答：

> "你有什么手段？"

能力不是工具本身。

关系：

```
Capability

↓

Tool
```

例如：

Capability：

```
Code Modification
```

对应：

Tools：

```
read_file

write_file

run_test

git_diff
```

---

为什么分离？

因为：

未来工具会变化。

但是能力稳定。

---

例如：

今天：

```
Web Search
```

使用：

Google API

未来：

使用：

其他搜索服务。

Agent 不需要修改。

---

# 七、Knowledge（知识层）

## 定义

回答：

> "你知道什么？"

来源：

* 系统知识
* 用户记忆
* 项目上下文
* 文档

结构：

```
Agent Knowledge

+

User Memory

+

Project Context

+

Runtime Information
```

---

注意：

Knowledge 不等于 Memory。

区别：

Knowledge：

> Agent知道什么。

Memory：

> Agent记住用户什么。

---

# 八、Planning（规划层）

## 定义

回答：

> "这个任务怎么完成？"

---

输入：

User Goal

例如：

```
帮我做一个网站
```

---

Planner 输出：

```
Goal:

创建网站


Steps:

1. 确认需求
2. 创建项目结构
3. 编写页面
4. 测试运行
5. 优化
6. 交付
```

---

Planner 不负责：

执行。

只负责：

路线。

---

# 九、Execution（执行层）

## 定义

回答：

> "现在具体做什么？"

---

Execution 接收：

```
Task Step
```

例如：

```
创建首页文件
```

判断：

```
需要：

Filesystem Capability
```

调用：

```
write_file()
```

---

执行结果：

返回：

```
Success

or

Failure
```

---

# 十、Observation（观察层）

新增。

很多 Agent 缺少这一层。

执行不是结束。

Agent需要观察环境变化。

例如：

修改代码：

↓

观察：

```
编译结果

错误日志

运行状态
```

---

结构：

```
Action

↓

Environment Change

↓

Observation
```

---

# 十一、Verification（验证层）

## 定义

回答：

> "任务真的完成了吗？"

---

验证方式：

### 文件任务

检查：

```
文件存在
内容正确
```

---

### 代码任务

检查：

```
是否编译
是否测试通过
```

---

### 写作任务

检查：

```
是否符合要求
格式是否正确
```

---

如果失败：

返回：

Planner。

形成循环：

```
Plan

↓

Execute

↓

Observe

↓

Verify

↓

Replan
```

---

# 十二、Agent Runtime Loop

最终：

```
              User Goal

                  ↓

          Understanding

                  ↓

              Planning

                  ↓

              Execute

                  ↓

             Observation

                  ↓

             Verification

                  ↓

          Completed Result

                  ↓

              User
```

如果失败：

```
Verification

↓

Planning

↓

Retry
```

---

# 十三、Agent 状态机

Agent 不应该只有：

聊天状态。

应该有：

```
IDLE

↓

UNDERSTANDING

↓

PLANNING

↓

EXECUTING

↓

VERIFYING

↓

COMPLETED

↓

FAILED
```

---

这样 UI 才能未来展示：

例如：

```
正在分析项目...

正在读取文件...

正在测试代码...
```

而不是：

一直显示：

"正在思考"。

# 十六、最终理念

MfkAgent 不应该成为：

> 一个拥有很多人格的聊天软件。

而应该成为：

> 一个能够理解目标、规划任务、调用能力并完成工作的个人 AI 工作系统。

---

这里有一个关键判断：

**Agent 的核心不是"更像人"，而是"更像一个可靠的工作伙伴"。**

下一步应该继续设计：

**《MfkAgent Agent Runtime Prompt Architecture》**

也就是：

> 这个 Agent 内部到底如何组织 System Prompt、Behavior、Planner、Tool、Memory 的组合。

因为现在我们定义了"身体结构"，下一步要设计"大脑运行机制"。
