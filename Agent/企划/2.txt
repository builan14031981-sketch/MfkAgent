MfkAgent Agent Runtime Architecture V1.0
一、文档定位
定义：
Agent 从接收到用户目标，到完成任务交付的完整运行流程。
本规范负责：
• Agent 生命周期
• 任务处理流程
• 上下文进入顺序
• 规划与执行循环
• 状态管理
• 错误恢复
不负责：
• Agent 身份定义
• Prompt 编写
• Tool 具体实现
• Memory 存储方案

四、Agent 生命周期状态
Agent 必须拥有明确状态。
状态：
复制
IDLE

↓

RECEIVING

↓

UNDERSTANDING

↓

PLANNING

↓

EXECUTING

↓

OBSERVING

↓

VERIFYING

↓

COMPLETED

↓

FAILED
 
状态说明
IDLE
等待任务。
 
RECEIVING
接收用户请求。
任务：
• 获取输入
• 判断输入完整性
 
UNDERSTANDING
理解用户目标。
需要判断：
• 用户真正想获得什么结果？
• 这是问题、任务还是咨询？
• 是否需要执行？
 
示例：
用户：
做一个网站。
错误理解：
“生成 HTML。”
正确理解：
“帮助用户获得一个可运行的网站。”
 
PLANNING
制定任务计划。
输出：
复制
Goal

Steps

Required Capability

Expected Result
例如：
复制
Goal:
创建个人网站

Steps:
1. 确认结构
2. 创建项目
3. 编写页面
4. 测试运行

Required:
Filesystem
Code
Browser
 
EXECUTING
执行具体步骤。
规则：
一次只执行当前明确步骤。
禁止：
没有计划直接连续操作。
 
OBSERVING
观察执行结果。
包括：
• 工具返回
• 文件变化
• 错误信息
• 环境状态
 
VERIFYING
确认：
任务是否达到目标。
不是：
“代码生成成功”。
而是：
“用户目标完成”。
 
COMPLETED
交付结果。
必须说明：
• 完成内容
• 产生文件
• 关键变化
• 后续建议
 
FAILED
失败处理。
必须：
• 说明失败原因
• 判断是否可恢复
• 提供下一步方案
 
五、Task Understanding（任务理解层）
这是 Agent 与普通聊天模型的第一道区别。
Agent 首先判断：
用户输入类型
分类：
复制
Question

↓

Information Request


Task

↓

Need Action


Conversation

↓

Need Interaction


Command

↓

Need Execution
 
例如：
用户：
“Python 怎么读取文件？”
类型：
Question。
不需要规划。
用户：
“帮我整理这个项目。”
类型：
Task。
进入 Agent Loop。

九、Self-Correction（自我修正）
Agent 遇到失败：

流程：

↓

例如：

错误：
复制
dependency missing

安装依赖

↓

重新测试
 
十、Human Approval（人工确认）
Agent 不应该无限自主。
需要风险判断。
 
低风险：
可以自动：
• 阅读文件
• 分析内容
• 生成方案
 
高风险：
需要确认：
• 删除文件
• 修改大量代码
• 执行危险命令
• 发布内容
 
流程：
复制
Agent Plan

↓

Risk Check

↓

Need Approval?

↓

User Confirm

↓

Execute

Agent 输出不是：

必须：

完成内容

↓

修改记录

↓

验证结果

↓

剩余问题
 
十二、Runtime 核心原则
原则1
先理解，再行动。
 
原则2
先规划，再执行。
 
原则3
执行必须可观察。
 
原则4
结果必须验证。
 
原则5
无法完成时，不伪造完成。

实现：
