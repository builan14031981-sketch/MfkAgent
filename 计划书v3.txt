# 五、已知技术债（Windows 兼容性审计 2026-08-02 + 后续发现）

### P0（阻塞打包/交付）
1. **打包产物为空**：`next.config.js` `output: 'export'` 被注释 → 需启用并补 `generateStaticParams`
2. **Electron 不启动后端**：`main.js` 无 spawn uvicorn 逻辑 → 需主进程 spawn 并退出时 taskkill 清理进程树
3. **存储路径依赖 CWD**：`config.py` 全部相对路径 → 需改为基于 `__file__` 绝对路径，清理根目录遗留 db
4. **services/tools.py 无沙箱**：FileRead/Write/ListDirectory 零校验 → 需补沙箱、subprocess 显式 UTF-8
5. **孤儿进程/端口占用**：无进程树清理、端口硬编码无检测 → 需 before-quit/session-end 清理、端口检测

### P1（功能受损）
- Windows 关机阻塞、subprocess GBK 乱码、os.walk 穿越 junction、长路径 MAX_PATH、SVG 图标不兼容、无国内 Electron 镜像、无单实例锁、next.config.js/ts 并存、沙箱大小写敏感、无开机自启

### P2（低风险）
- 导出文件名非法字符、UPLOAD_DIR 死配置、electron@28 旧版本、start.sh trap 仅 Unix 有效、根目录遗留 GBK 编码文档

# 附录 A：Memory 自动提取系统计划书 V1.0

## 1. 当前状态
### 已实现
- MemoryItem 数据模型、CRUD API、Global/Agent/Project 三层作用域
- `add_memory` 工具、对话时 Memory 注入 system prompt

### 当前缺陷
- 依赖模型主动发现（易忘记、行为不一致、用户无法确认）
- 缺少记忆生命周期管理（值得保存/去重/过期/更新）

## 2. V1 目标
> 在不引入复杂 RAG 的情况下，让 Agent 能够稳定识别并保存长期有效信息。

范围：
✅ 自动提取长期记忆  
✅ 记忆类型分类  
✅ 记忆去重  
✅ 用户可查看/删除  

不做：
❌ 向量数据库  
❌ 自动复杂推理  
❌ 多 Agent Memory 共享  
❌ Memory 智能推荐

## 3. 新增架构
### 3.1 Memory Extractor
`backend/app/services/memory_extractor.py`

输入：用户消息 + AI回复 + 已有 Memory  
输出：
```json
[
  { "type": "preference", "content": "用户喜欢 Apple 风格 UI", "confidence": 0.92 }
]
```

### 3.2 提取触发时机
V1：聊天结束后触发。

### 3.3 Memory 类型设计
| 类型 | 说明 | 示例 |
|------|------|------|
| preference | 用户偏好 | 喜欢简洁 UI、喜欢代码先分析后执行 |
| fact | 用户事实 | 使用 Windows、开发 MfkAgent |
| project | 项目规则 | MfkAgent V1 不允许用户创建 Agent |
| workflow | 工作习惯 | 喜欢先规划再执行 |
| temporary | 临时信息 | 默认不长期保存 |

### 3.4 提取规则
只允许保存：长期稳定信息（"以后都使用 TypeScript"）  
禁止保存：临时/一次性信息（"今天电脑坏了"、"这次报错"）

### 3.5 去重机制
保存前查询已有 Memory，语义相似则合并而非新增。

### 3.6 用户控制
新增 Memory 页面：展示分类记忆、支持查看/删除/编辑。

# 附录 C：Tool Runtime V5 工具闭环修复记录（2026-08-05）

## 1. 背景
用户观察到：连续执行 `run_command` 工具后，对话以空回复结尾、无 AI 总结；前端工具卡片也不显示结果。

## 2. 根因（DB 实证：chat 99 msg 704/708）
- `chat_stream()` 循环 `range(max_tool_rounds + 1)`（max_tool_rounds=8 → 共 9 轮），模型每轮调工具都 `continue` 占 1 轮，9 次调用把轮次耗尽 → 生成器静默结束、无总结轮、内容为空。
- 带结果的 `{"tool_calls": 汇总}` 事件只在正常结束路径 yield，轮次耗尽时从未发出。
- 实时 `{"tool_call": ...}` 事件缺 `result` / `tool_call_id` 字段。
- 前端 `useChatStream.ts` 去重键为 `(path, name)`，所有 `run_command` 的 `path=""` → 折叠成 1 张卡；`ToolCallCard.tsx` 不显示工具名与完整结果。
- 意图规则缺失："检查当前项目修改 / 查看当前项目有没有改动 / git 状态" 等不匹配 → `need_tools=False` → 命令被模型当纯文本输出。

## 3. 后端修复（已完成并验证，后端 AI 交付）
| 文件 | 修复内容 |
|------|----------|
| `backend/app/services/model.py` | ① `chat_stream()`：`round_tools = tools if round_no < max_tool_rounds else None`，末轮移除工具强制模型输出总结；② 工具分支守卫 `and round_tools`；③ 实时事件补 `result`/`tool_call_id`；④ 循环后兜底：轮次耗尽时用累积消息发起无工具收尾请求，`yield {"finish_reason":"stop"}` + `yield {"tool_calls": 汇总}`；⑤ `_chat_openai_compatible()`：每轮在累积消息上执行（修复前轮上下文丢失 bug）+ 轮次预算后补无工具总结请求 |
| `backend/app/core/tool_runtime/intent.py` | 新增 `git_operation` 意图规则（git 状态/修改/提交/日志、检查/查看/看看项目、项目改动/修改/变更、改了什么/有哪些改动 等） |
| `backend/app/core/tool_runtime/planner.py` | `_intent_tool_map` 增加 `"git_operation": ["run_command", "git_status", "git_diff", "git_log"]` |

**验证结果**（qwen-flash 实测）：
- 流式：3 次 `run_command` 实时事件均含 `result`+`tool_call_id`；结束后正常输出 694 字总结；汇总事件含全部 6 字段。
- 非流式：`finish_reason=stop`，工具后输出 281 字总结。
- 意图："检查当前项目修改 / git 状态 / 看看这个项目改了什么" 等均命中 `git_operation`。

## 4. 前端任务清单（待前端 AI 执行，后端已就绪）
| 编号 | 文件 | 任务 |
|------|------|------|
| F-1 | `frontend/src/hooks/useChatStream.ts` | 工具去重键由 `(path, name)` 改为 `tool_call_id`（兜底 `path+name+index`），使多次 `run_command` 显示为独立卡片 |
| F-2 | `frontend/src/components/ToolCallCard.tsx` | 增加工具名标签（如 `run_command` / `git_status`）+ `result` 完整内容可展开查看；失败（`success=false`）样式区分 |

## 5. 遗留
- `observer.py`（`core/tool_runtime/`）为死代码（未被 import），非本次问题原因，暂不处理。
- 工具执行完后由模型生成的总结为模型行为，受模型与 `max_tool_rounds` 预算约束；如需更严格可后续接入变更交付摘要（Phase 11 项 14.3）。
